# Integration feasibility — Phase 00

Public sources checked **2026-11-24** against [the integration contract](INTEGRATIONS.md). **No real user export or authenticated API response was supplied or inspected.** Documented fields, examples, app features and data-collection policies are not evidence of actual account coverage. No authorization URL was used, no account was accessed, and no import or sync was tested. Costs, quotas, historical coverage and platform or account entitlements are unverified unless specifically noted below. “Unverified” does not mean the provider offers no route.

## Source findings

| Source | Verified from public documentation | Status and next evidence needed |
|---|---|---|
| Lyfta | Checked 2026-11-24: [Developer docs](https://my.lyfta.app/community/api) and [OpenAPI](https://my.lyfta.app/openapi.json) document free personal bearer keys, read-only OAuth scope `training:read`, paginated workout history, UTC date filters, and limits of 60 requests/minute and 5,000/day. The [public sandbox](https://my.lyfta.app/api/sandbox/v1/workouts) supplied two sample workouts with nested sets. | **Authorization required; real import unverified.** Local page validation passed against public samples. Need an owner-authorized real response, load-unit provenance and revision behavior before canonical import. Native export and actual history coverage remain unverified. |
| Bend | [Official site](https://www.bend.app/) describes routines and tracking in the iOS/Android app. The [privacy URL](https://www.bend.app/privacy) returned product content in this check; neither response established an export contract. | **Unverified.** Check app settings or vendor support for dated completed sessions, duration and region metadata. Leave mobility coverage unavailable without records; a routine catalog is not session history. |
| BetterMe | [Privacy policy](https://betterme.world/privacy-policy) describes access requests and opt-in writes from some products to Apple Health or Health Connect for workouts, weight and dietary energy. It does not establish a desktop API or a portable workout/wellness schema. | **Unverified** for direct import. Prefer an owner-supplied portability sample; any Health Connect route needs approval and proof of which records the exact app/version writes. Do not assume meditation, HRV or other collected wellness data is shared. |
| How We Feel | [Privacy policy](https://howwefeel.org/privacy) describes emotions, check-in date/time, tags and optional journal or attachments; without an account, records stay on the iOS/Android device and the provider cannot access them. The policy documents access requests and conditional portability; the [FAQ](https://howwefeel.org/faq) yielded no usable instructions in this check. | **Unverified.** Confirm whether the installed app can export locally and what fields it includes; for account-held data, a user-initiated access request is a fallback. Pilot emotion, timestamp and tags; keep notes, location and attachments out of the shared sample. |
| FatSecret | [Food diary v2](https://platform.fatsecret.com/docs/v2/food_entries.get) documents personal profile entries via three-legged OAuth 1.0, distinct from public food search; [v1](https://platform.fatsecret.com/docs/v1/food_entries.get) is deprecated. V2 documents date or entry-ID reads, JSON/XML, meal category, servings, kcal/macros and optional nutrients; it does not document exact meal time. The docs index lists monthly diary and weight methods. V2 lists only entry, food and serving IDs as storable values. | **Authorization required; persistence compatibility unresolved.** Before any API adapter, verify access to the owner's existing consumer history, permissions, backfill, quota/edition cost and whether terms allow offline storage of nutrients and raw payloads. Prefer an owner-supplied diary/weight export if available and permitted; no export format verified. |
| MDF | No unambiguous app identity in the V2 integration spec. | **Unverified; identity blocked.** Obtain full name, publisher, store link or package ID and platform. Then check for a supported export with dated completions and stable habit IDs. |
| Strava | [Export help](https://support.strava.com/hc/en-us/articles/216918437-Exporting-your-Data-and-Bulk-Export) documents web-account bulk archive and per-activity original files (often FIT), TCX and GPX; GPS-based formats may omit indoor/non-GPS sessions. The [API reference](https://developers.strava.com/docs/reference/) documents OAuth 2.0 athlete activity reads (`activity:read`, `activity:read_all` for Only Me), paginated history with time filters, activity IDs, dates, distance, durations, speed, elevation and optional heart-rate streams. [Rate limits](https://developers.strava.com/docs/rate-limits/) document default non-upload limits of 100/15 min and 1,000/day, overall 200/15 min and 2,000/day, and single-athlete capacity for new apps. | **Documented export; import unverified.** First Fedora file-import candidate: request a small owner-provided original file or activity-only subset of a bulk archive. Verify time zones, units, GPS and HR presence, and coverage of indoor and older activities. API **authorization required**; confirm actual app limits, costs and terms for local retention before sync. |
| Zepp | [Corporate policy](https://www.zepp.com/privacy-policy) excludes app data; the separate [Zepp App policy](https://upload-cdn.zepp.com/tposts/8192) documents data access/portability requests and optional sharing with providers including Strava. It lists HR, HRV, sleep, steps, workouts and SpO₂ as data the app/device may collect, not as guaranteed export fields. | **Unverified** for direct desktop import. Ask for a Zepp App portability sample and exact device/app version. If the owner already shares workouts with Strava, test those as a workout-only fallback; do not infer recovery, sleep or other metrics from that route. |
| Google Fit / Health Connect | Google's [migration guide](https://developer.android.com/health-and-fitness/health-connect/migration/fit) says Fit APIs including REST are supported through end of 2026; the [Fit FAQ](https://developers.google.com/fit/faq) documents consent and relevant Fitness scopes. Health Connect uses Android on-device permissions by record type, not desktop OAuth. The [read guide](https://developer.android.com/health-and-fitness/health-connect/read-data) documents steps and HR reads, paging and rate limiting, a default lookback to 30 days before first grant for other apps' data, and separate history/background permissions where supported. Actual records depend on what source apps write. | **Do not build new legacy Fit sync. External bridge required** for direct reads from Health Connect into Fedora; no bridge approved or tested. Prefer a supported user-provided file if available. Google's migration guide points to Google Health API for cloud integrations; it does not establish access to this user's legacy history. |
